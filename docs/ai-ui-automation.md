# 传统 UI 自动化 vs AI UI 自动化：各脆在哪，各用在哪

> 这段认知比会背 Playwright API 值钱。面试被问「AI 自动化能不能取代传统自动化」时，直接按下面四层答。

## 0. 一句话

**传统自动化脆在「选择器漂移」，AI 自动化脆在「多模态误识别」；前者是确定性系统的维护成本问题，
后者是概率系统的可信度问题。** 所以不是替代关系，是分工关系：核心链路用确定性方案兜底，
长尾场景和快速改版的页面用 AI 换维护人力。

## 1. 传统自动化：脆在选择器

选择器为什么会漂：

| 漂移来源 | 例子 | 后果 |
| --- | --- | --- |
| DOM 结构调整 | 加了一层 `<div>`、`<button>` 换成 `<a role="button">` | `.btn-primary > span` 直接失效 |
| 文案/多语言改版 | 「立即购买」→「马上抢」 | `getByText('立即购买')` 全红 |
| 样式重构 | CSS Modules 哈希类名 `.btn__x7f2a` | 类名选择器不可维护 |
| 组件库升级 | Ant Design 3 → 4，弹层挂载点变化 | 等待逻辑、作用域全部要重写 |

它的**本质缺陷**不是"选择器写法不好"，而是**测试代码与 UI 实现细节强耦合**：UI 改一版，
测试跟着改一遍；UI 改得越快，测试维护成本越高，最后团队干脆不维护，套件腐烂。

它的**不可替代的优点**：完全确定。同一个输入，永远同一个结果；失败必然可复现；
失败信息直接指向"哪个元素不存在"，排障路径短。

缓解手段（写进用例规范，而不是靠个人自觉）：

1. 选择器优先级：`getByRole` / `getByLabel` > `data-testid` > 文本 > CSS/XPath（禁用）。
2. 语义化定位：优先用用户能感知的 role + name。
3. 用 `web-first assertion`（`expect(locator).toBeVisible()`）代替 `sleep`，把 flaky 交给框架重试。
4. 关键流程配视觉快照，锁定"不该变的像素"，改版时由人判断差异是否合理。

## 2. AI 自动化：脆在多模态

以 Midscene.js 这类「截图 + 视觉语言模型 → 输出坐标/操作」的方案为例，失败模式完全不同：

| 失败模式 | 具体表现 | 为什么难排 |
| --- | --- | --- |
| 相似元素混淆 | 页面有三个「抽一次」样式的按钮，点到弹窗里那个 | 报告里只有"点了"，没有"为什么选它" |
| 视觉退化 | 深色模式、低分辨率、缩放 125%、字体加载未完成 | 人眼看正常，模型看到的截图不一样 |
| 遮挡与浮层 | Toast / 引导蒙层盖住目标 | 点击落到蒙层上，断言超时 |
| 非确定性 | 同一页面两次描述，一次成功一次失败 | 不可重放，重跑可能就绿了 → 掩盖真 bug |
| 成本与延迟 | 每次 aiAction 一次多模态调用，秒级 + 按量计费 | 100 条用例的 CI 成本不可忽略 |
| 断言模糊 | "页面显示成功"——模型说成功，其实提示的是"提交失败" | 断言变成了另一个模型的判断，可信度下降 |

**它的本质优势**：不依赖 DOM 细节。改版、换框架、甚至换端（H5/小程序/桌面），
只要"人看到的界面"没变，用例就还能跑。对**改版频繁、元素不稳定、多端复用**的场景，
维护成本的下降是数量级的。

## 3. 对比表（可以直接背）

| 维度 | 传统自动化 | AI 自动化 |
| --- | --- | --- |
| 定位方式 | DOM 结构 / 语义角色 | 截图 + 视觉理解 |
| 稳定性来源 | 选择器契约 | 模型识别准确率 |
| 失败信号 | 元素找不到，定位明确 | 识别偏差，原因不透明 |
| 可复现性 | 确定 | 概率性 |
| 维护成本 | 随 UI 改版线性上升 | 与 DOM 解耦，随"视觉变化"上升 |
| 执行速度 | 毫秒级 | 秒级 + 网络/模型延迟 |
| 成本 | 近乎零 | 按调用计费 |
| 最怕什么 | 改版、重构、多语言 | 相似元素、视觉退化、模糊断言 |
| 最适合 | 核心链路、回归基线、性能敏感 | 长尾场景、快速改版页、一次性验证、探索 |

## 4. 我的组合策略（这才是面试要听的"你怎么落地"）

1. **单测保业务**：抽奖概率、排行榜排序这类纯逻辑，用 pytest 参数化覆盖，
   跑得快、定位准。UI 层永远不重复验证这些规则。
2. **传统 E2E 保核心链路**：登录、下单、支付——链路稳定、改动少、错了代价大，
   用确定性方案兜底，配 trace / 截图 / 视频。
3. **AI 补长尾与探索**：新页面刚上线、需求三天一改、或者要快速验证"这个流程能不能走通"时，
   用自然语言先跑通，再决定要不要固化成脚本。
4. **AI 的产出必须落地成确定脚本**：探索阶段用 AI，进入回归集之前转成选择器版本
   （record → review → codegen）。**回归集里不允许存在概率性用例**，否则套件会失去"红=有问题"的语义。
5. **AI 断言只做辅助**：视觉断言可以用来发现"看起来不对"，但不能替代业务断言（金额、状态、幂等）。

## 5. 怎么衡量值不值

| 指标 | 传统 | AI | 说明 |
| --- | --- | --- | --- |
| 首次通过率 | 高（写对了就过） | 低（模型波动） | AI 需要重试策略 |
| 单条用例修复成本 | 高（改版必改） | 低（视觉不变就不用改） | AI 的收益在这里 |
| 误报率 | 低 | 高 | 误报会摧毁团队对套件的信任 |
| 单次执行成本 | 低 | 高（模型调用） | 决定 AI 只能覆盖长尾 |

结论：**用 AI 降维护成本，用传统保确定性**。谁便宜谁上，但"回归门禁"必须由确定性方案把守。

## 6. 三句话面试口径

> 传统自动化的问题是测试代码和 UI 实现细节绑死，选择器一漂就全红，维护成本随改版频率线性增长；
> AI 自动化把定位交给视觉模型，跟 DOM 解耦，但换来的是概率性——相似元素、模糊断言、成本延迟都是新问题。
> 所以我的做法是分层：核心链路用确定性脚本兜底，长尾和快速迭代的页面用 AI 探索，进入回归集前必须固化成确定脚本。
